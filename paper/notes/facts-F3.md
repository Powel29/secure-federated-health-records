## A. Library and primitive inventory

1. Standard primitives come from pyca `cryptography`; every `cryptography.hazmat` import is confined to `src/crypto_core/` (the module docstrings state the rule). — `src/crypto_core/symmetric.py:1-15`, `src/crypto_core/asymmetric.py:1-11`, `src/crypto_core/__init__.py:1-6`
2. Charm-Crypto was rejected because it depends on the PBC and GMP C libraries, has patchy Python 3 support, and typically costs teams one to two weeks to build; multi-authority attribute-based access is on the critical path, so the build risk was judged unacceptable. — `ARCHITECTURE.md:30-35`; `docs/adr/0001-reject-charm-crypto.md` (Status: Accepted)
3. As a consequence, three constructions are hand-rolled: Shamir secret sharing over a prime field, an ElGamal-style PRE, and the policy-tree access structure. — `ARCHITECTURE.md:21-23`; `docs/adr/0001-reject-charm-crypto.md:19-22` (Status: Accepted)
4. AEAD is AES-256-GCM via pyca `AESGCM`; the key must be exactly 32 bytes, or the call raises `ValueError`. — `src/crypto_core/symmetric.py:19`, `:82-90`, `:117-120`
5. The GCM nonce is 12 bytes (96 bits), drawn fresh from `secrets.token_bytes` on every encryption. `aes_gcm_encrypt` takes no nonce parameter; it returns `(ciphertext_with_tag, nonce)`. — `src/contracts/base.py:60`, `src/crypto_core/symmetric.py:38-51`, `:54-90`; `docs/adr/0022-aes-gcm-no-caller-nonce.md` (Status: Accepted, ratified 2026-09-06)
6. The GCM tag length is not set in our code. It is pyca `AESGCM`'s fixed 16-byte tag, appended to the ciphertext: a 32-byte plaintext encrypts to 48 bytes (computed). Decryption fails closed with `InvalidTagError` on a tag mismatch. — `src/crypto_core/symmetric.py:88-89`, `:125-128`
7. Key and randomness generation uses `secrets` (stdlib CSPRNG): `generate_key` = `secrets.token_bytes(32)` by default; the Shamir coefficients use `secrets.randbelow(P)`; the ElGamal exponents use `secrets.randbelow(q-2)+2`. No `random` import exists under `src/` (grep). — `src/crypto_core/symmetric.py:22-35`, `src/shamir/finite_field.py:18-28`, `src/pre/elgamal.py:34-36`
8. KDF is HKDF with SHA-256 (pyca `HKDF`), default output 32 bytes, caller-supplied salt and info. — `src/crypto_core/symmetric.py:131-158`
9. HKDF salt/info labels in use: PRE KEM salt `b"pre-key-encapsulation-salt"`, info `b"pre-symmetric-key"`; search tokens salt `b"search-token-v1"`, info `b"health-record-search:" ‖ normalised term`. — `src/pre/elgamal.py:30-31`, `src/search/service.py:32-34`
10. The hash is SHA-256 (pyca `hashes.SHA256`), 32-byte digest. It is used for the audit hash chain `h_i = SHA-256(h_{i-1} ‖ event ‖ timestamp ‖ actor)`, whose genesis previous-hash is 32 zero bytes, and for the emergency-assertion digest. — `src/crypto_core/symmetric.py:161-175`, `src/contracts/base.py:59`, `src/audit/chain.py:3`, `:43`, `:96`, `src/breakglass/assertion.py:219`
11. Signatures are ECDSA on curve SECP256R1 (P-256) with SHA-256 and DER-encoded signatures. Verification raises `InvalidSignatureError` on failure (fail closed) and never returns False. — `src/crypto_core/asymmetric.py:1`, `:27`, `:45`, `:67-71`
12. EC private keys serialise as PKCS#8 PEM (optionally under pyca `BestAvailableEncryption` with a password); public keys serialise as SubjectPublicKeyInfo PEM. — `src/crypto_core/asymmetric.py:74-98`, `:126-138`
13. X.509 certificates are real pyca `x509` objects on P-256 keys, signed ECDSA-with-SHA-256. They carry BasicConstraints (critical) and a SubjectKeyIdentifier, have a bounded `valid_days` window, and may carry an optional role in the subject OU (ADR-0064). A public key that is not EC is rejected. — `src/crypto_core/x509_certs.py:32-90`, `:205-217`
14. Signed, hashed and AAD byte strings are built by `encode_fields(domain, fields)`: a UTF-8 domain tag, then every field, each with a 4-byte big-endian length prefix. Its own docstring says it is an encoding, not a cryptographic construction. — `src/crypto_core/encoding.py:1-43`; `docs/adr/0077-domain-tagged-length-prefixed-encoding.md` (Status: Proposed)
15. "Key wrapping" in this code base is AES-256-GCM with structured AAD, not AES-KW (RFC 3394) and not RSA-OAEP: no RSA or AES-KW primitive exists under `src/` (grep for `rsa|oaep|keywrap` finds nothing). — `src/records/service.py:121-165`; see Contradictions C1
16. Anti-replay nonces in assertions and envelopes are at least 16 random bytes (128 bits). — `src/contracts/base.py:61`

## B. Group and field parameters (demonstration strength)

17. Shamir field: GF(P) with `P = 2^256 + 297`. This is a 257-bit prime (primality checked with 40-round Miller–Rabin, computed), chosen so that any 256-bit block embeds as a field element. Each 32-byte secret block becomes a 33-byte share element. — `src/shamir/finite_field.py:1-15`
18. ElGamal/PRE group: the order-q subgroup of Z*_P, where `SAFE_PRIME_P = 0xF45C8BBE…F73667` is a 256-bit safe prime (`P = 2q+1`, q a 255-bit prime; both checked with Miller–Rabin, computed) and generator `g = 4`, a quadratic residue (checked: `4^q ≡ 1 mod P`). — `src/pre/elgamal.py:21-24`; `docs/adr/0018-crypto-spike-findings.md:42-47` (Status: Accepted, ratified 2026-09-06)
19. The 256-bit safe-prime ElGamal group is a demonstration parameter, not a production one, and the paper must say so. The ADR names ECDH on P-256 through `crypto_core` as the production choice. Every ElGamal use inherits this: PRE, the break-glass DEK delivery KEM, and share sealing. — `docs/adr/0079-shares-travel-sealed.md:55-57` (Status: Proposed); `src/breakglass/share_sealing.py:26-27`; `PROJECT.md:406-410` (§5 item 11)
20. A 256-bit finite-field discrete-log group falls far short of the ≥2048-bit moduli that standard key-size guidance requires. *(External fact: the writer must cite NIST SP 800-57 Part 1 or equivalent directly; it is not in the repo.)*
21. ElGamal exponents are drawn uniformly from `[2, q-1]`. Every caller-supplied group element (the public key in `encrypt_point`, `c1` in `reencrypt` and `decrypt_point`) is checked for order-q subgroup membership (`1 < x < P` and `x^q ≡ 1 mod P`) before exponentiation, and fails closed with `PREKeyError`. `c2` and the message point are deliberately left unchecked. — `src/pre/elgamal.py:34-47`, `:109-110`, `:138-141`, `:164-167`; `docs/adr/0023-pre-subgroup-validation.md` (Status: Accepted, ratified 2026-09-06)

## C. Shamir secret sharing (hand-rolled)

22. `split_secret(secret, k, n)` prefixes the secret with its 4-byte big-endian length and zero-pads it to a multiple of 32 bytes. Each 32-byte block gets an independent random polynomial of degree k−1 over GF(P), evaluated at x = 1..n. A share is `(x, concatenated 33-byte y values)`. — `src/shamir/split.py:27-76`
23. A 32-byte secret yields 66-byte shares (two blocks). An AND child share re-split by a nested AND yields 99-byte shares, so share size grows with AND depth. — computed with `src/shamir/split.py:split_secret`; growth noted in `docs/adr/0026-policy-engine-cryptographic-enforcement.md:81-84` (Status: Accepted)
24. `combine_shares` fails closed on missing, duplicate-x, x outside `1..P-1`, ragged-length, out-of-field y, oversize-block, or corrupt-length-header input. It interpolates at x = 0 with Lagrange coefficients. Shares are not authenticated: a well-formed but wrong share yields a wrong secret, and the AES-GCM unwrap downstream detects it. — `src/shamir/split.py:79-163`, `src/shamir/finite_field.py:72-87`

## D. Record envelope layout

25. Each record gets a fresh 256-bit DEK from the CSPRNG, and its payload is encrypted with AES-256-GCM under that DEK. — `src/records/service.py:56-60`, `src/records/ingest.py:170-181`
26. The `Record` contract fields, in order: `record_id`, `patient_id`, `facility_id`, `policy_id`, `content_type`, `ciphertext` (AES-256-GCM output including the tag), `nonce` (validated as exactly 12 bytes), `aad` (optional), `created_at`, `clinical` (labels). Binary fields are base64 in the contract. — `src/contracts/records.py:16-46`
27. The payload AAD is optional (`aad: bytes | None = None`), and the facility ingest endpoint passes none. In the shipped ingest path the payload ciphertext is therefore not bound to `record_id` or other metadata by GCM; only the DEK wrapping is (fact 29). — `src/records/service.py:27`, `:60`; `src/api/hospital.py:1917-1929`
28. The `DEKWrapping` contract fields, in order: `wrapping_id`, `record_id`, `wrapped_for` (policy id, or `"emergency"`), `wrapped_dek`, `nonce` (exactly 12 bytes), `generation` (≥ 0, incremented on re-wrap), `created_at`. — `src/contracts/records.py:49-80`
29. DEK wrapping is AES-256-GCM of the 32-byte DEK under a 32-byte wrapping key, with AAD = `encode_fields("ehr/dek-wrapping/v1", [record_id, wrapped_for, str(generation)])`. A wrapping therefore cannot be moved to another record or policy or replayed as a different generation. `wrapped_dek` is 48 bytes (computed). — `src/records/service.py:108-118`, `:121-165`, `:168-195`; `docs/adr/0077-domain-tagged-length-prefixed-encoding.md:36-37` (Status: Proposed)
30. At ingest each record gets two wrappings of the same DEK. One is under the policy root secret (`wrapped_for = policy_id`, generation 0). The other is under the record's emergency key (`wrapped_for = "emergency"`, generation 0). — `src/records/ingest.py:198-226`
31. A record's search terms are serialised as a JSON array and sealed with AES-256-GCM under the record's DEK, with AAD `b"health-record-search-terms-v1:" ‖ record_id`, so that expiry and revocation can re-index. They are stored as `record_search_terms(record_id, ciphertext, nonce[12])`. — `src/search/service.py:39`, `:54-95`; `src/storage/migrations/0005_service_auth_and_rotation.sql:10-18`; `docs/adr/0069-full-rotation-at-expiry.md` (Status: Proposed)

## E. Access structure: Shamir over a policy tree (CP-ABE substitute)

32. Policy node types are exactly `LEAF`, `AND` and `OR`. There is no general k-of-n threshold gate in the policy tree. — `src/contracts/enums.py:66-71`
33. Compilation runs top-down from a 32-byte root secret. An AND node with m children Shamir-splits its incoming secret m-of-m (`split_secret(secret, k=m, n=m)`) and records each child's x. An OR node passes the same secret to every child. A leaf AES-256-GCM-encrypts its incoming secret under the attribute key with a fresh nonce. — `src/policy/engine.py:177-226`; `ARCHITECTURE.md:150-155`; `docs/adr/0026-policy-engine-cryptographic-enforcement.md:34-50` (Status: Accepted)
34. The root secret is the DEK wrapping key: at ingest a fresh 32-byte root secret is generated, the tree is compiled under it, and the DEK is wrapped under it. — `src/records/ingest.py:190-206`; `src/policy/engine.py:7`; `ARCHITECTURE.md:155`
35. Leaf shares are sealed with AES-256-GCM and no AAD (`aes_gcm_encrypt(key=key, plaintext=secret)`), so a leaf ciphertext is not cryptographically bound to its record, node position or attribute. — `src/policy/engine.py:192`
36. Attribute keys are symmetric 32-byte keys, keyed `(authority_id, attribute.name, attribute.value)`, so a key for the same `name:value` from another authority does not open the leaf. Each authority mints one stable key per owned `(name, value)` and refuses names outside its namespace. — `src/policy/engine.py:42-49`, `:88-90`; `src/authority/issuance.py:149-176`
37. One attribute key per (authority, attribute value) is shared by every holder and never rotated. Revoking a credential stops future releases, but a holder who already has the key keeps it. — `PROJECT.md:393-399` (§5 item 9); `src/authority/issuance.py:151-153`
38. Reconstruction runs bottom-up. A leaf is decrypted with the held key; a missing key or bad tag counts as "unsatisfied". OR takes the first child that succeeds. AND needs every child and then `combine_shares(k=m)`. If the root is unsatisfied the call raises `PolicyDeniedError`; it never returns a partial or default secret. — `src/policy/engine.py:276-336`
39. `evaluate_policy` is a keyless boolean PDP. Enforcement (the PEP) is `reconstruct_root_secret` / `unwrap_dek_via_policy`, which release nothing unless the held keys decrypt the tree. — `src/policy/engine.py:19-22`, `:108-144`, `:339-365`
40. Every record's tree is authored as `OR(clinical_policy, owner:<patient_id>)`, where the owner leaf is owned by the patient's home authority. On revocation the owner leaf's authority is taken from the stored tree, never from the caller. — `src/policy/engine.py:368-397`; `src/records/revocation.py:130-173`
41. The structure is not collusion-resistant: two clinicians can pool attribute keys to satisfy a policy neither satisfies alone. Pairing-based CP-ABE prevents this; this construction cannot. It is not proven secure, and real CP-ABE is future work. — `ARCHITECTURE.md:162-166`; `docs/adr/0002-secret-sharing-access-structure.md:29-33` (Status: Accepted); `.claude/skills/ieee-paper/SKILL.md:43-48`

## F. Proxy re-encryption and the break-glass KEM

42. PRE scheme: ElGamal over the group in fact 18, with `pk = g^sk mod P`. Encryption of a group element M is `(c1, c2) = (g^k, M·pk^k)`. Re-encryption is `c1' = c1^rk` with `c2` unchanged. Decryption is `M = c2·c1^(−sk)`. — `src/pre/elgamal.py:50-61`, `:96-115`, `:118-144`, `:147-173`
43. The re-encryption key is `rk = sk_a · sk_b^(−1) mod q`; computing it requires both secret keys. It is bidirectional: `rk^(−1) mod q` is the B→A key. — `src/pre/elgamal.py:64-93`; `ARCHITECTURE.md:50-54`; `docs/adr/0076-pre-is-bidirectional.md` (Status: Proposed)
44. `reencrypt` and `generate_rekey` are never called outside `src/pre/` in production code (grep). Break-glass uses only the KEM. — grep over `src/`; `src/breakglass/gate.py:31-49`; `docs/adr/0076-pre-is-bidirectional.md:18-20`
45. KEM (`encapsulate_key`): pick a random subgroup element `point = g^r`, ElGamal-encrypt it under the recipient's `pk`, and derive a 32-byte symmetric key as `HKDF-SHA256(ikm = point as 32 bytes big-endian, salt = "pre-key-encapsulation-salt", info = "pre-symmetric-key")`. Decapsulation decrypts the point and re-derives the key. — `src/pre/elgamal.py:176-220`
46. Break-glass delivery: the gate reconstructs the emergency key from 3 unique shares (`combine_shares(k=3)`), unwraps the DEK at the facility, encapsulates a delivery key to the clinician's ElGamal PRE public key, and AES-256-GCM-encrypts the DEK under it with AAD = `record_id` (UTF-8). The facility therefore sees the DEK during the unlock. — `src/breakglass/gate.py:250-268`; `docs/adr/0076-pre-is-bidirectional.md:33-34`; `PROJECT.md:400-405` (§5 item 10)
47. Delivery package layout (fixed-length framing): `c1` (32 B) ‖ `c2` (32 B) ‖ GCM nonce (12 B) ‖ AES-GCM(DEK) (32 B + 16 B tag), so 124 bytes for a 32-byte DEK (computed). `pre.delivery.open_delivery_package` inverts it. — `src/breakglass/gate.py:87`, `:262-267`; `src/pre/delivery.py:23-71`
48. Threshold shares in transit are sealed with the same KEM. AES-256-GCM is applied under the encapsulated key with AAD = `encode_fields("ehr/sealed-share/v1", [record_id, x, recipient_id])`. Each recipient's ElGamal public key is published in a statement signed with its root-certified ECDSA service key over `encode_fields("ehr/share-sealing-key/v1", [service_id, kind, key])`. — `src/breakglass/share_sealing.py:1-27`, `:56-57`, `:100-112`, `:176-196`; `docs/adr/0079-shares-travel-sealed.md` (Status: Proposed)
49. The emergency key is 32 random bytes, generated per record when it is provisioned and split Shamir 3-of-4: x=1 goes to the clinician custodian, x=2 to the home authority, and x=3,4 to the audit service. — `src/breakglass/emergency_key.py:28-67`; `src/custodian/__init__.py:54-65`
50. No security proof exists for the PRE. Writers must not claim IND-CPA, unidirectionality or collusion resistance for it; the correct entry is "not proven". A unidirectional PRE (e.g. AFGH) needs pairings, which are out of scope. — `.claude/skills/ieee-paper/SKILL.md:41-48`; `docs/adr/0076-pre-is-bidirectional.md:37-38` (Status: Proposed)

## G. Emergency-scoped search

51. Search token: `coded_term = HKDF-SHA256(ikm = emergency_key, salt = b"search-token-v1", info = b"health-record-search:" ‖ UTF-8(term.strip().casefold()), L = 32)`. It is deterministic in (emergency key, normalised term) and not bound to `record_id`. — `src/search/service.py:32-34`, `:98-112`; `docs/adr/0027-search-token-construction.md:29-49`, `:113-118` (Status: Accepted, ratified 2026-09-06; amended 2026-10-13)
52. The store's index table is `search_index(id, record_id, coded_term bytea)`, one row per (record, term), and lookup is an equality match on `coded_term`. — `src/storage/migrations/0001_initial.sql:120-127`; `src/search/service.py:115-141`
53. At query time the token is derived from the record's live emergency key, which the expiry manager hands out only while a non-expired emergency session exists for that record. Otherwise it raises, so search fails closed outside Emergency-open. — `src/search/service.py:144-164`; `src/lifecycle/expiry.py:509-534`
54. On expiry/rotation a new emergency key is generated, the sealed term list is opened with the old DEK, and every token is re-derived under the new key, so old tokens stop matching. — `src/lifecycle/rotation.py:233`, `:265-280`; `docs/adr/0069-full-rotation-at-expiry.md` (Status: Proposed)
55. Leakage: tokens are deterministic, so under one emergency key equal terms give equal `coded_term` values (search- and access-pattern leakage, deterministic-SSE). The store also sees how many terms each record has. A test locks the equality leakage in as intended behaviour. — `docs/adr/0027-search-token-construction.md:62-69`; `src/search/service.py:4-7`; `src/storage/migrations/0001_initial.sql:123-127`
56. Each record has its own emergency key (fact 49), so tokens for the same term under different records' keys differ. The cross-record equality leakage in fact 55 therefore applies only to rows written under the same key. — `src/custodian/__init__.py:54-58`, `src/lifecycle/rotation.py:265`, `src/search/service.py:98-112`

## H. Revocation (crypto side)

57. The library revocation call verifies the actor's signed GRANTED→REVOKED event and checks that the actor is the patient or home authority. It recovers the old DEK through the current policy (the caller never supplies a DEK), then generates a fresh root secret and a fresh DEK, re-encrypts the payload, and re-wraps with `generation+1`. — `src/records/revocation.py:285-346`; `docs/adr/0036-revocation-by-key-rotation.md` (Status: Accepted, ratified 2026-09-06)
58. The deployed facility path no longer calls `revoke_record_access`. It re-keys through the expiry rotation, which also produces a new emergency key, new shares and a new search index. — `docs/adr/0080-revocation-without-keys-on-the-wire.md:36-45`, `:67-68` (Status: Proposed)

## Contradictions found

C1. **RSA-OAEP is listed but not implemented.** `ARCHITECTURE.md:18` and `docs/adr/0001-reject-charm-crypto.md:20` list RSA-OAEP among the pyca primitives, but no RSA or OAEP code exists under `src/` (grep). Code wins: the paper must not list RSA-OAEP.

C2. **The Shamir prime is 257 bits, not 256.** `ARCHITECTURE.md:21` says "GF(p) with p a 256-bit prime". The code uses `P = 2^256 + 297`, a 257-bit prime with 33-byte share elements (`src/shamir/finite_field.py:1-15`). Code wins.

C3. **PRE direction.** `docs/adr/0001-reject-charm-crypto.md:22` ("ElGamal-style unidirectional PRE"), `docs/adr/0018-crypto-spike-findings.md:42` ("toy unidirectional ElGamal PRE") and `docs/adr/0012-shrink-proxy-reencryption.md:11-13` ("without decryption") all describe a unidirectional, decryption-free scheme. The code is bidirectional, and the facility decrypts in break-glass (`src/pre/elgamal.py:64-93`, `src/breakglass/gate.py:253-259`). ADR-0076 (Proposed) corrects ADR-0012 but does not amend ADR-0001 or ADR-0018. Code wins.

C4. **Term normalisation.** The ADR-0027 Decision body (`docs/adr/0027-search-token-construction.md:48-49`) says tokens are case-sensitive and byte-exact. The code trims and case-folds (`src/search/service.py:106`), which matches the ADR's 2026-10-13 amendment (`:113-118`). No NFKC normalisation is applied. Code wins; cite the amendment.

C5. **Revocation steps in ADR-0036.** `docs/adr/0036-revocation-by-key-rotation.md:34-35` says the old DEK is caller-supplied, and `:49-51` says the function does not enforce who may revoke. The code recovers the DEK through the policy and enforces authorization (`src/records/revocation.py:285-308`). The deployed path no longer uses this function at all (ADR-0080). Code wins.

C6. **ADR file and title numbering differ.** `docs/adr/0080-revocation-without-keys-on-the-wire.md:1` is titled "ADR-0073". Cite it by file path to avoid confusion.

C7. **Scope of the search leakage statement.** `src/search/service.py:5-7` and ADR-0027 (`:62-64`) say two records indexing the same term produce identical `coded_term`s. That holds only under a shared key, and the shipped path gives every record its own emergency key (`src/custodian/__init__.py:54-58`). This is a scope nuance rather than a contradiction: state the leakage per emergency key.

C8. **Stale comment in the gate.** The `src/breakglass/gate.py:46-47` docstring says the clinician-side DEK recovery "lives in the API layer (Phase 4)". It actually lives in `src/pre/delivery.py:29-71` (whose docstring notes this). This is comment drift with no effect on behaviour.
