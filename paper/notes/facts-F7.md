## Methodology (harness)

12. One command regenerates every number: `DATABASE_URL=... python -m bench.run_benchmarks` (full) or `--no-db` (crypto subset). Benchmarks never run in CI. — `bench/README.md` lines 3-12; `bench/run_benchmarks.py:1-11`
13. Timer: `time.perf_counter()` around each single call, converted to ms. — `bench/run_benchmarks.py:83-85`
14. Warm-up: 5 untimed calls per benchmark (default `--warmup 5`), discarded. — `bench/run_benchmarks.py:56, 78-79`; `benchmark_summary.csv` column `warmup`
15. Iterations: 30 timed calls per latency benchmark (default `--iterations 30`, minimum 2). — `bench/run_benchmarks.py:55, 81-85, 722-723`; `benchmark_summary.csv` column `iterations`
16. Statistics: median (`statistics.median`), p95 (`statistics.quantiles(values, n=100, method="inclusive")[94]`, i.e. interpolated at n=30), mean, min, max. — `bench/run_benchmarks.py:69-72, 88-94`
17. No outlier removal, no GC control, no CPU pinning; every timed sample is kept. — `bench/run_benchmarks.py:75-94`
18. Ciphertext expansion is a single deterministic measurement per size (`iterations=1`), not a timing. — `bench/run_benchmarks.py:361-394`
19. The latency plot is a box plot of raw samples on a log y-axis with whiskers at p5-p95; the expansion plot is expansion % against plaintext size (log2 x-axis). The paper must take numbers from the CSV, not the PNGs. — `bench/run_benchmarks.py:647-677`; ieee-paper skill "Quoting benchmark numbers"
20. The four crypto benchmarks and ciphertext expansion run in-process before any server starts; the three DB benchmarks run inside `standalone_federation`, while six uvicorn servers and two expiry monitors run in the same process. — `bench/run_benchmarks.py:741-765, 407-410`; `demo/driver.py:399-404, 459-461`

## In-process vs transport

21. In-process (no HTTP, no DB): `threshold_reconstruction`, `rewrap_cost`, `revocation_latency`, `pre_reencryption_component`, `ciphertext_expansion`. — `bench/run_benchmarks.py:160-394`
22. HTTP, including transport: `cross_facility_latency` and `emergency_search_latency`. Both are real HTTP requests over loopback (`http://127.0.0.1:<port>`, plain HTTP, no TLS) to uvicorn servers running in daemon threads of the benchmark's own Python process, sent through a client that signs every request (ADR-0066). — `bench/run_benchmarks.py:418, 447-449, 529-537`; `demo/driver.py:168-186, 293, 399-404`; `deploy/bootstrap.py:269-285`
23. Both HTTP endpoints make a nested, synchronous signed HTTP call to the audit service (which appends to the Postgres hash chain) before responding, so the HTTP figures include a second HTTP hop and a Postgres write. — `src/api/hospital.py:1768-1780, 1857-1868, 278-309`; `demo/driver.py:338`
24. `audit_verification` uses no HTTP but includes a Postgres read of the whole chain over psycopg, then signature and hash-link verification. — `bench/run_benchmarks.py:569-577`; `src/audit/chain.py:476-477`
25. HTTP figures depend on the machine and DB path. Earlier runs of the same harness measured ~15 ms (WSL), ~170 ms (native Windows), ~49-51 ms (AMD 16-core, 2026-10-19), ~405 ms (this Intel machine, 2026-10-21, before ADR-0089) and ~247/241 ms (this run, same Intel machine). — `WORKFLOW.md` P5-2 lines 547-551

## Ciphertext expansion

33. Measured as `len(record.ciphertext)` from `encrypt_record` on plaintext `b"A" * size`; that field is AES-256-GCM ciphertext plus the 16-byte tag. It excludes the 12-byte nonce (stored separately), AAD, DEK wrappings, compiled policy, Shamir shares and search index entries. — `bench/run_benchmarks.py:361-394`; `src/records/service.py:60-72`; `src/contracts/base.py:60`
34. Rows (plaintext bytes -> ciphertext bytes, expansion %): 64 -> 80, 25.0; 256 -> 272, 6.25; 1024 -> 1040, 1.5625; 4096 -> 4112, 0.390625; 16384 -> 16400, 0.09765625. The overhead is a constant 16 bytes. The source has `expansion_percent`, not a ratio column. — `benchmark_results.csv` rows `ciphertext_expansion` (`parameters` plaintext_bytes=64 ... 16384)

## Contradictions found

C1. `environment.json` says `local-processes+postgres`, but the federation in the benchmark is one Python process with six uvicorn servers in daemon threads, and the benchmark client shares that process (and GIL). `demo/driver.py:198`'s docstring says "five federation service processes"; the code starts six servers. Code wins: describe it as "six services on loopback in one Python process, Postgres in Docker Desktop". — `bench/run_benchmarks.py:730`; `demo/driver.py:168-176, 198, 399-404`; `WORKFLOW.md:550`

C2. The benchmark-methodology skill requires recording "whether the run was local processes or Docker" and a results schema `bench/results/<metric>__<timestamp>.csv` with `n_patients, n_facilities, run_index, bytes_in, bytes_out` plus request IDs. The harness writes `benchmark_results.csv`/`benchmark_summary.csv` with neither those columns nor request IDs, and `environment.json` omits Postgres's location, commit hash and library versions. — `.claude/skills/benchmark-methodology/SKILL.md` "Output format", "Correlating with the traffic captures"; `bench/run_benchmarks.py:603-645`

C3. The benchmark-methodology skill lists "re-wrap / proxy-re-encryption cost vs. record count"; the harness measures a single DEK and a single PRE ciphertext. `PROJECT.md` D4 says only "re-wrap cost", which the harness does satisfy. — skill "What gets measured"; `PROJECT.md:54`; `bench/run_benchmarks.py:185-219, 336-353`

C4. `bench/README.md` says the benchmarks "are the seven metrics PROJECT.md D4 requires", but its table lists eight rows: `pre_reencryption_component` is an extra one beside `rewrap_cost`. — `bench/README.md` lines 34-43; `PROJECT.md:54`

C5. The harness comment says latency values "span ~5 us to ~20 ms"; this run spans 0.0094 ms to 319.9 ms (HTTP medians ~240-250 ms). The comment is stale. — `bench/run_benchmarks.py:647-648`; `benchmark_summary.csv`

C6. WORKFLOW attributes HTTP latency changes to "the machine and DB path, not the code", but the same Intel machine measured ~405 ms and then ~247 ms on the same day (the code changed only in the share split between the runs). HTTP figures therefore also vary run to run on one machine; quote them as indicative only. — `WORKFLOW.md:550-551`

C7. `ARCHITECTURE.md` describes Shamir over "GF(p) with p a 256-bit prime"; the code uses p = 2^256 + 297, which is a 257-bit prime. This matters only if the paper states the Shamir field size next to the combine timing. — `ARCHITECTURE.md:21`; `src/shamir/finite_field.py:3, 12-13`

C8. Not a contradiction in the numbers: `federation.get("audit_app")` is always `None` because `standalone_federation` yields no such key, so the audit public key is fetched over HTTP (untimed setup). — `bench/run_benchmarks.py:558-567`; `demo/driver.py:451-457`

C9. `docs/explainers/07-honest-limits-and-what-we-found.md:88` still describes the harness as built with numbers "to be" produced. It is stale. It is an explainer, not a source.
