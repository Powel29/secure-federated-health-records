## A. Threat model: status, assets, trust assumptions

1. `docs/threat-model.md` is task P0-4/T04, owner Ojas, and says of itself "Draft status — needs Ojas's sign-off before Phase 0 closes." — `docs/threat-model.md:3-4`
2. The threat model treats four adversaries as separate threats (adopted from the external review, `PROJECT.md` §4B), because each is stopped by a different design property and one (colluding clinicians) only partially. — `docs/threat-model.md:6-12`
3. Governing principle: cryptographic authorization decides whether a key can be reconstructed; endpoint authorization decides whether a request should have been served; both run, endpoint check first. — `docs/threat-model.md:14-17`
4. Assets, in priority order: PHI plaintext; per-record DEKs (AES-256-GCM); the emergency key (reconstructed from the weighted 3-of-4 Shamir gate, ADR-0089); attribute keys; audit-chain integrity; metadata (explicitly not claimed hidden; search leakage is measured and break-glass is observable as metadata). — `docs/threat-model.md:21-37`
5. Trust assumption: AES-256-GCM, ECDSA, SHA-256, HKDF and Shamir are assumed sound; breaking AES is not modelled. — `docs/threat-model.md:41-42`
6. Trust assumption: the HSM/KMS emergency timer is a trusted (simulated, ADR-0003) process; a compromised timer could decline to expire a key, but expiry is a signed, logged rotation, so subversion is tamper-evident rather than prevented (`PROJECT.md` §5 item 2). — `docs/threat-model.md:43-47`; `PROJECT.md:339-342`
7. Trust assumption: each service holds its own signing key, and its local key/state DB is not leaked except where an adversary is defined to compromise it. — `docs/threat-model.md:48-49`
8. Out of scope by decision (threat model): rate-limiting, MFA, session and transport-confidentiality threats; breaking primitives; production web-app threats; a malicious HSM timer beyond the signed-rotation mitigation; real patient data (synthetic only). — `docs/threat-model.md:50-54,185-194`
9. The audit service is a trusted party: the chain is a plain hash chain it holds (ADR-0034); stored-entry tampering is detected (C5) and a facility refuses a truncated chain (ADR-0083), but a compromised audit service could release share 3 without a durable entry or show different chains to different parties (no proofs of presence/extension). "No log entry, no key" holds against everyone except the audit service. — `PROJECT.md:419-429` (§5 item 13, ADR-0088). Not stated in `docs/threat-model.md` §2 (see Contradictions).
10. The key custodian is a trusted shared process in the demo (ADR-0043): it holds every synthetic persona's signing key, PRE key and credentials and signs on their behalf after portal login; it holds share 1 only. — `PROJECT.md:352-358` (§5 item 5)
11. The audit service is a single point of availability for break-glass: shares 3 and 4 are held only by the audit service, so break-glass needs it plus either the custodian (share 1) or the home authority (share 2); the home authority covers a lost share 1 only. — `PROJECT.md:381-392` (§5 item 8); `src/breakglass/emergency_key.py:29-30` (`THRESHOLD = 3`, `TOTAL_SHARES = 4`)
12. The patient's home authority is trusted to issue the patient's attributes, including the `owner:<patient_id>` key (ADR-0016); a rogue home authority could mint that key and read all that patient's records. — `docs/threat-model.md:135-142`

## B. Adversaries

13. **Adversary A — shared store (honest-but-curious; also fully compromised/dumped).** The single central `store` process (port 8000) holding all ciphertext, wrapped keys and the coded search index (ADR-0011). Can read all it stores, observe access patterns and timing; HBC does not deviate from protocol. — `docs/threat-model.md:58-66`
14. Adversary A cannot get keys or plaintext (AES-256-GCM records, wrapped DEKs, coded index). Residual: access pattern, query volume, response sizes (measured, `PROJECT.md` §4A item 3), and metadata (records per patient, that a break-glass occurred). Stopped by envelope encryption and the store never being a key custodian. — `docs/threat-model.md:68-78`
15. **Adversary B — hacked hospital node.** One facility (e.g. `facility-a`, port 8001) fully attacker-controlled: process, local DB of clinician certs, home-authority link, signing key. Can forge requests as that facility, present held certificates, attempt reads/break-glass, replay captured requests, act outside its remit. — `docs/threat-model.md:80-88`
16. Adversary B cannot decrypt beyond its held attribute keys; cannot forge break-glass alone (needs three of four shares, two held only by the audit service, released only after a log commit); replay is blocked by one-time IDs on assertions, share requests and transition events; a forged Emergency Assertion fails signature/binding/expiry checks before any share is requested. Residual: reads what its legitimate keys authorize; can enumerate reachable patient IDs (threat model says bounded "by a test (P5-1)"); forward-only revocation. Stopped by threshold gate + log-before-share + replay IDs + per-request crypto authz. — `docs/threat-model.md:90-109`
17. **Adversary C — rogue attribute authority.** Mints keys for attributes it owns, signs under its authority certificate, acts as a patient's home authority and so holds share 2, released only against an assertion it validated itself (ADR-0089). — `docs/threat-model.md:111-121`
18. Adversary C cannot satisfy trees needing other authorities' attributes; share 2 alone or with the custodian's share 1 cannot reconstruct the emergency key. Residual: policies satisfiable entirely by its own attributes, and the ADR-0016 owner key. Stopped by multi-authority policy trees + threshold gate; "Partially". — `docs/threat-model.md:123-145`
19. **Adversary D — colluding clinicians (attribute pooling).** Two or more clinicians pooling different legitimate attribute keys to satisfy a policy none satisfies alone. Not stopped: the Shamir-over-policy-tree structure is not collusion-resistant (no per-user binding as in pairing-based CP-ABE); documented limitation, CP-ABE is future work. — `docs/threat-model.md:147-168`; `PROJECT.md:345-351` (§5 item 4)
20. Summary table: A — fully for plaintext, leakage measured; B — fully, beyond what its own keys permit; C — partial; D — no. — `docs/threat-model.md:172-179`
21. No adversary in `docs/threat-model.md` models a compromised audit service, compromised key custodian, or network/on-path attacker; these appear only as trust assumptions/caveats in `PROJECT.md` §5 items 5, 8, 11, 13. — `docs/threat-model.md:58-179`; `PROJECT.md:352-429`

## C. The claim registry (`tests/security/claims.py`)

22. Claims C1–C11 are defined in the `CLAIMS` dict, sourced from `CONVENTIONS.md` §5's ten exit-criterion tests plus ADR-0016 (C11). — `tests/security/claims.py:44-96`
23. Every claim-bearing test carries `@pytest.mark.claim("Cn", level=...)`, `level="module"` (control holds inside its module) or `level="system"` (holds through the running services). — `tests/security/claims.py:3-6`
24. Tagged tests are found by a pytest `--collect-only` subprocess with the plugin `tests.security._claim_collector`; a non-zero collection exit raises `ClaimCollectionError` (the table is void) rather than silently dropping tests (review N3). — `tests/security/claims.py:132-153`; `tests/security/_claim_collector.py:19-38`
25. `run()` executes every tagged node id in a subprocess and records per-node outcomes `passed`, `failed`, `skipped`, `xfailed`, `xpassed`, `error`; a missing node is "never ran". — `tests/security/claims.py:156-172`; `tests/security/_claim_collector.py:44-59`
26. Status computation (`claim_status`), considering **system-level tests only**: no system test → `NO SYSTEM TEST`; collection only → `NOT RUN (collection only)`; any system test outcome not in {passed, skipped, xfailed} (i.e. failed, error, xpassed, not run) → `BROKEN: <nodeids>`; else any xfailed → `fails today: <xfail reasons>`; else any skipped → `UNVERIFIED (skipped)`; else → `holds`. Module-level outcomes never affect the status. — `tests/security/claims.py:175-201`
27. A failing system test is kept at full strength and marked `xfail(strict=True, reason="<finding>")`, so the run turns red when the fix lands (ADR-0046). — `tests/security/claims.py:10-14`
28. CLI: `python -m tests.security.claims` prints one `Cn: <status>` line per claim; `--table` prints a markdown table with columns Claim, Statement, Status, Module tests, System tests (xfail tests suffixed "(xfail)"); `--collect-only` lists without running, so no claim can show as holding. It runs the claim-tagged tests and needs Postgres. — `tests/security/claims.py:16-19,204-245`
29. Postgres-backed tests skip when `DATABASE_URL` is unset/unreachable, but fail when `CI=true` (review F42), so a CI run cannot silently drop C2/C5 Postgres evidence; a laptop run without Postgres yields `UNVERIFIED (skipped)` for affected claims. — `tests/security/conftest.py:1-38`
