## A. Module scope and deliverable standard

1. The course requires each project to **implement and demonstrate** at least one module from a faculty list. A mention alone does not count. — `PROJECT.md:206-208`
2. The selected module is Module 7, Traffic Analysis (Wireshark, PyShark). It is the only module chosen. Module 4 (PCAP to XML/SQLite) was considered and dropped. — `PROJECT.md:210-217`
3. The module is delivered as PyShark analyser code that asserts the properties automatically, not as screenshots. "An analyser that fails when plaintext appears, or when a share precedes a commit, is a test." — `PROJECT.md:259-262`
4. Plain HTTP is captured on purpose, and the same scenario is captured again under TLS. The plain capture is the positive control that proves the detector finds secrets when they are present. — `PROJECT.md:226-232`
5. Four properties must be established: (1) no plaintext on the wire under TLS, (2) commit-before-release is externally verifiable, (3) searchable-encryption leakage is measured, and (4) break-glass is observable as metadata but not as content. — `PROJECT.md:234-257`
6. "No plaintext on the wire" holds **under the TLS profile only** (D6-b, ADR-0073). On the plain profile, no read, revocation or break-glass request carries a private signing key, and threshold shares travel sealed (ADR-0079). Record plaintext, DEKs and attribute keys do cross, because the facility encrypts and decrypts server-side. — `PROJECT.md:237-247`, `PROJECT.md:406-411` (§5 item 11)
7. Client-side crypto in the key agent (D6-a) is future work. — `PROJECT.md:246-247`, `PROJECT.md:411`, `docs/adr/0073-claim-1-scoped-to-tls.md:38-40`

## B. Capture scope and enforcement in code

8. Capture uses `dumpcap`, which ships with Wireshark/tshark. If `dumpcap` is not on PATH, `CaptureToolUnavailable` is raised rather than faking a capture. — `wire/capture.py:19-22`, `wire/capture.py:126-133`
9. The allowed interfaces are an explicit allowlist. Loopback: `lo`, `lo0`, `\Device\NPF_Loopback`, `Adapter for loopback traffic capture`. Docker bridge: `docker0`, or `br-` followed by exactly 12 lowercase hex characters (Docker's user-defined bridges). — `wire/capture.py:73-84`, `wire/capture.py:104-110`
10. Any other interface is refused before capture starts. `capture_scenario` raises `CaptureInterfaceRefused`, and the CLI exits with argparse error code 2. — `wire/capture.py:165-167`, `wire/capture.py:273-274`; tests `tests/wire/test_capture.py::test_shared_network_interfaces_are_refused` (eth0, Wi-Fi, en0, wlan0, br-, any, br-lan, br-ex), `tests/wire/test_capture.py::test_cli_refuses_a_shared_interface_with_exit_2`, `tests/wire/test_capture.py::test_loopback_and_bridge_interfaces_are_allowed`
11. The default interface is the platform loopback (`lo` on Linux, `lo0` on macOS, `\Device\NPF_Loopback` on Windows). — `wire/capture.py:64-68`, `wire/capture.py:113-117`; test `tests/wire/test_capture.py::test_every_platform_default_is_allowed`
12. A BPF filter pins capture to TCP on the federation's own ports plus the Postgres port: `tcp and (port … or …)`. — `wire/capture.py:120-123`; test `tests/wire/test_capture.py::test_bpf_filter_pins_only_federation_ports`
13. The service ports are authority-med 8010, authority-net 8011, audit 8020, facility-a 8001, facility-b 8002 and custodian 8030, which makes six HTTP services. — `wire/tls.py:22-29`
14. The Postgres port comes from `DATABASE_URL`, falling back to 5432. This project's Postgres listens on 55432/55433. — `wire/capture.py:48-59`; test `tests/wire/test_analyser_false_passes.py::test_db_port_defaults_to_database_url`
15. Raw PCAPs are written to `wire/captures/`, which is git-ignored. Only the analysers and their assertions are committed. — `ARCHITECTURE.md:484-487`, `wire/capture.py:44`
16. The p53 runs were captured with dumpcap on `\Device\NPF_Loopback`, with BPF on the six federation ports plus Postgres 55432. Environment: Windows 11 10.0.26300, Python 3.11.17, TShark 4.6.9, Postgres 16. — `bench/results/p53_search_leakage.md` ("How the captures were taken")
17. A capture that dumpcap aborted, or that wrote nothing, raises `CaptureFailed`. Any older pcap at the output path is deleted first, so it can never be analysed by mistake. — `wire/capture.py:170-172`, `wire/capture.py:191-203`; test `tests/wire/test_analyser_false_passes.py::test_failed_capture_never_leaves_an_old_pcap_to_analyse`

## D. Analyser pipeline (what every check rests on)

23. PyShark reads every payload-carrying TCP segment (`display_filter="tcp.len > 0"`). This is the only PyShark-dependent step in the checks. — `wire/streams.py:127-157`
24. Checks run on reassembled TCP byte streams, one per (stream, direction) in sequence order, never per packet. Retransmissions are de-duplicated, and each byte offset maps back to its frame and timestamp. — `wire/streams.py:1-11`, `wire/streams.py:75-111`; tests `tests/wire/test_streams_and_canaries.py::TestReassembly::*`
25. A lost segment is recorded as a gap. A canary match may not span a gap, and any gapped service flow makes claim 1 "inconclusive", which counts as a FAIL. — `wire/streams.py:53-56`, `wire/canaries.py:131-134`, `wire/checks.py:172-183`; tests `tests/wire/test_analyser_false_passes.py::test_flow_with_missing_segment_makes_claim1_inconclusive`, `::test_match_is_never_invented_across_a_gap`
26. HTTP messages are split by the project's own parser (keep-alive, chunked bodies) over the reassembled bytes. tshark's HTTP dissector is not used for the checks. — `wire/http_messages.py:62-151`, `docs/adr/0045-p5-5-wire-claim-checks.md:88-90`; tests `tests/wire/test_streams_and_canaries.py::TestHttpSplitting::*`
27. The scenario writes a canary manifest of every secret it handled, stamped with `run_id` and `started_at`. It holds 13 canaries: `record_plaintext` (phi), `dek`, `emergency_key`, `share1`–`share4` (share), `share3_sealed` (sealed_share, not a secret), four attribute keys, and `clinician_signing_key_pem` (private_key). — `deploy/run_scenario.py:750-789`, `deploy/run_scenario.py:1050-1070`, `deploy/run_scenario.py:257`
28. Each canary is searched in every plausible encoding: raw bytes, lowercase and uppercase hex, standard and URL-safe base64 at all three byte alignments, and PEM body lines for keys. Patterns under 16 characters are not searched. A manifest with an unsearchable canary is rejected. — `wire/canaries.py:76-120`, `wire/canaries.py:31`, `wire/canaries.py:56-73`; tests `tests/wire/test_streams_and_canaries.py::TestCanaryEncodings::*`, `tests/wire/test_analyser_false_passes.py::test_manifest_with_unsearchable_canary_is_rejected`
29. JSON bodies are also checked against a denylist of key-carrying fields: `plaintext_b64`, `emergency_key_b64`, `share_hex`, `key_b64`, `holder_keyring`, `attribute_keyring`, `old_dek_b64`, and any `*_signing_key_pem`. — `wire/checks.py:58-69`, `wire/checks.py:127-151`
30. A pcap whose every frame predates its manifest's `started_at` is refused as stale. — `wire/analyze_traffic.py:62-80`; test `tests/wire/test_analyser_false_passes.py::test_stale_pcap_older_than_manifest_rejected`
31. Precondition (claim 0): the plain capture must show all nine scenario endpoints, including `/records/rec-001/revoke`. No manifest may be empty. The TLS capture must expose zero HTTP exchanges and must show TLS records (`0x16 03`/`0x17 03`) on every service port the plain run used. — `wire/analyze_traffic.py:42-55`, `wire/analyze_traffic.py:102-138`; tests `tests/wire/test_analyser_false_passes.py::test_tls_capture_with_single_handshake_fails_preconditions`, `tests/wire/test_live_capture.py::test_preconditions_reject_an_incomplete_plain_capture`
32. Claims 1–4 run only if the preconditions pass. The CLI exits non-zero if any claim fails, using explicit checks rather than `assert`. — `wire/analyze_traffic.py:197-216`, `wire/analyze_traffic.py:13-14`
33. The analyser writes `bench/results/p55_wire_checks.json` (one object per claim) and `bench/results/p55_search_leakage.csv`. — `wire/analyze_traffic.py:186-191`, `wire/analyze_traffic.py:141-165`

## F. Commit-before-release (claim 2)

43. Property: the audit service's Postgres `COMMIT` for the release entry crosses the wire **before** the `/breakglass/release` HTTP response that carries shares 3 and 4, sealed to the facility gate (ADR-0079, ADR-0089). The sealed share 3 must first appear inside that response. Only the audit service's release counts; a home authority's share-2 release commits nothing. — `wire/checks.py:20-25`
44. How ordering is read from packets, step 1. The check finds the answered `/breakglass/release` exchange whose request went to the audit port (8020), requires HTTP 200, and requires an `entry` object in the response JSON. — `wire/checks.py:298-324`
45. Step 2. The first appearance of the `share3_sealed` canary (bytes unique to this release) must lie inside the release response's byte span. Otherwise the check fails with "share 3 crossed the wire at frame X, before the release response". — `wire/checks.py:326-347`, `wire/checks.py:123-124`
46. Step 3. The check takes `event_type` from the release request body and finds it as a text bind parameter on the client-to-Postgres stream (the latest occurrence at or before the response). On the reverse stream of the same connection, it finds the first Postgres `CommandComplete("COMMIT")` (`C 00 00 00 0b COMMIT 00`) at or after that INSERT. — `wire/checks.py:349-357`, `wire/checks.py:264-295`, `wire/checks.py:76`
47. Step 4. It fails if no INSERT+COMMIT is found (the DB port must be captured **unencrypted**, so claim 2 runs on the plain capture only) or if `commit_ts > response timestamp`. Otherwise `commit_lead_ms = (response_ts − commit_ts) × 1000`. Ordering comes from capture timestamps and TCP stream identity. No request id or chain-head value is matched. — `wire/checks.py:357-393`
48. ADR-0045 rejected the alternative of proving claim 2 from the response contents plus a later `/chain/verify`. Share and entry arrive in the same response, which shows the entry exists but not that it was committed first. — `docs/adr/0045-p5-5-wire-claim-checks.md:84-87`
49. Claim 2 result: **PASS**, strength `strong`: "audit COMMIT acknowledged 1.35 ms before the release response". Values: `release_response_frame` 414, `first_share3_frame` 416, `release_entry_seq` 4, `db_port` 55433, `db_insert_ts` 1792588199.857699, `db_commit_ts` 1792588199.8597183, `commit_lead_ms` 1.3468. Computed from those: the INSERT-to-COMMIT time is about 2.0 ms. — `p55_wire_checks.json` `[2]` (`2-commit-before-release`)
50. Only share 3's sealed bytes are timed. Share 4 travels in the same response, but no separate canary times it. — `wire/checks.py:55`, `wire/checks.py:329`; `deploy/run_scenario.py:764-770`
51. Claim 2 tests: `tests/wire/test_checks.py::TestClaim2CommitBeforeRelease::test_commit_before_response_passes`, `::test_commit_after_response_fails`, `::test_share_on_wire_before_release_fails`, `::test_a_capture_without_the_sealed_share_canary_fails_closed`, `::test_missing_db_traffic_fails_closed`, `::test_no_release_exchange_fails`.

## Contradictions found

C1. **ARCHITECTURE.md vs ADR-0073 / PROJECT.md / results.** `ARCHITECTURE.md:476` says `capture-plain` "Demonstrates that confidentiality comes from application-layer encryption, not from TLS" and calls it the primary evidence profile. `ARCHITECTURE.md:477` calls TLS "secondary … defence in depth". The code (`wire/checks.py:168-256`, default scope `tls`) and the results contradict this: `p55_wire_checks.json [1].evidence.plain_hits` shows record plaintext, the emergency key and attribute keys readable on plain. PROJECT.md §4A item 1 and §5 item 11 agree with the code. **The code and PROJECT.md win.** ARCHITECTURE §7 is stale.

C2. **DEKs on the plain wire: docs vs results.** `PROJECT.md:244-245`, `PROJECT.md:409-410` and ADR-0073 (lines 13, 29) say DEKs cross in clear on the plain profile. In the 2026-10-21 p55 run, the `dek` canary had **no** hit in the plain capture (`[1].evidence.plain_hits` lists only attribute keys, `emergency_key` and `record_plaintext`), and no `old_dek_b64` denylisted field appears. Either the docs overstate it, or that run's DEK traffic took a form that was not searched. Only "plaintext, the emergency key and attribute keys" are evidenced in clear; don't cite the docs for DEKs without re-checking.

C3. **The claim-2 mechanism, worded differently.** `PROJECT.md:248-250` frames the ordering against "the log-commit response containing the new chain head". The code establishes ordering from the Postgres `CommandComplete("COMMIT")` on the audit service's DB connection, compared by capture timestamp with the first byte of the `/breakglass/release` HTTP response (`wire/checks.py:264-393`). It requires an `entry` object in the response but never reads or matches a chain head or request id. **The code wins.** Describe the DB-COMMIT ordering.

C4. **Help text and docstrings vs the code default.** `wire/analyze_traffic.py:177` help says "all: … (default)", but the actual default is `tls` (`:176`). `tests/wire/test_live_capture.py:8-9` docstring says the default is `all`, but the code default is `tls` (`:42`). `docs/adr/README.md:60` (the ADR-0045 row) still says "`all` default", though its status column notes ADR-0073. **Code wins:** the default is `tls`.

C5. **Interface rule message vs code.** The `CAPTURE_RULE` text (`wire/capture.py:87`) and `ARCHITECTURE.md`/`CLAUDE.md` say Docker bridges are `br-*`. The code accepts only `br-` + 12 hex characters (`wire/capture.py:84`), and `br-lan`/`br-ex` are refused by test. The code is stricter.

C6. **Number of services.** `PROJECT.md:219` ("five-process federation") and `ARCHITECTURE.md:476,482` ("all five services") disagree with `wire/tls.py:22-29` (six HTTP services, custodian included, plus Postgres) and with the p53 md ("six federation ports plus Postgres"). **Code wins:** six HTTP services plus the store.

C7. **ADR-0045 vs the current claim-2 code.** ADR-0045 (lines 40-42) says share 3 must not appear "outside custody setup" before the release response. The code (post-ADR-0079) instead requires the first appearance of the *sealed* share-3 bytes to lie inside the release response (`wire/checks.py:326-347`). This is a refinement, not a conflict in outcome. Cite the code.

C8. **Evidence age, not a contradiction.** The p55 claim-3 run measured only 1 search. All multi-search leakage numbers come from the p53 files of 2026-10-19 (built at `0b95f2b`+branch), which predate the ADR-0089 commit `99092d1` that changed `deploy/run_scenario.py` and the break-glass services. `src/search` is unchanged since then, but the skill requires runs from the commit the paper describes, so state the p53 date and build, or re-run.
