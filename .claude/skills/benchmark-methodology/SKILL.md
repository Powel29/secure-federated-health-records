# Benchmark methodology

The evaluation section is where a reviewer looks for reasons to disbelieve the
rest of the paper. Numbers that cannot be reproduced, or that were measured in
a way that flatters the system, undermine claims that are otherwise sound.

## What gets measured

From `PROJECT.md` D4:

- revocation latency
- break-glass threshold-reconstruction time
- emergency-search latency
- re-wrap / proxy-re-encryption cost vs. record count
- audit-log verification cost
- cross-facility access latency
- ciphertext expansion per record
- scalability against number of patients and number of facilities

## Measurement rules

**Warm up before measuring.** Discard the first runs. Python's first pass
through a code path includes import resolution, JIT-free interpretation of cold
bytecode, and connection setup. Reporting cold-start timings as steady-state
latency overstates cost and invites a question you cannot answer.

**Repeat, and report a distribution.** Never report a single run. Take at least
30 repetitions and report median plus p95, not the mean. Cryptographic
operations on a loaded laptop produce long tails; a mean hides them and a p95
is what an examiner asks about.

**Record the environment with the numbers.** CPU model, core count, RAM, Python
version, OS, and whether the run was local processes or Docker. A benchmark
without its environment cannot be compared to anything, including your own
later runs.

**Separate the crypto from the transport.** Cross-facility latency includes HTTP
overhead that has nothing to do with the contribution. Measure and report the
cryptographic operation separately from the round trip, or the interesting
number disappears inside network noise.

**Benchmarks are not tests.** They live in `bench/` and never run in CI. A slow
CI is a CI people learn to skip.

## Output format

Write results to a fixed schema so that plots, tables, and the paper's numbers
all regenerate from one command. Re-running an analysis must never mean
re-running the benchmark by hand.

```
bench/results/<metric>__<timestamp>.csv
  metric, n_patients, n_facilities, run_index, duration_ms, bytes_in, bytes_out
bench/results/env__<timestamp>.json
  cpu, cores, ram_gb, python, os, deployment_path
```

The analysis script reads these; it does not take numbers as arguments. If a
figure in the paper cannot be regenerated by running one command against a
results file, it is not reproducible and should not be in the paper.

## Plots

Use the `data:create-viz` or `data:data-visualization` skills for the plotting
mechanics. Beyond those:

- Label axes with units. `duration_ms`, not `time`.
- Show the distribution where it matters — for latency, prefer a box plot or a
  median line with a p95 band over a bare bar chart.
- Scalability curves need the x-axis parameter named exactly as it appears in
  the results schema, so a reader can match figure to data.
- Do not truncate a y-axis to make a difference look larger. It is the single
  most common way an honest result becomes a dishonest figure.

## Correlating with the traffic captures

Requests carry a request ID (see `ARCHITECTURE.md` §8). Record it in the
benchmark output so a timing row can be matched against the corresponding
packets in the PCAP analysis. This is what lets the evaluation say something
about *what was on the wire during the operation that took this long* rather
than treating the two as separate exercises.

## Honesty

Report the numbers you got, including the unflattering ones. Proxy
re-encryption and threshold reconstruction may be slow; that is a finding, and
a paper that reports a cost and explains it is stronger than one that omits it.
If a result looks too good, check the measurement before celebrating — the most
likely explanation is that the benchmark is not exercising the path it claims.
